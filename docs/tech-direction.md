# 技術・アート方針（v2）

ステータス: **確定**（2026-10-11、オーナー指示により再定義）。[direction.md](direction.md) の 4〜6 章（性能目標・アセット・作り込みの重点）はこの文書で置き換える。
変更する場合はこの文書を更新し、理由を残す。

## 0. 前提となる姿勢

- 目標は**コンシューマーゲームの傑作と並べて遜色ない一場面**。ブラウザ・WebGPU・スマホ対応は制約であって、品質を下げる理由ではない。
- 制約は**設計で吸収する**。重い計算はオフラインへ（焼き込み）、見せない所は見せない（視線と構図の設計）、足りない所はゲームの演出で補う。
- 垂直スライスは小さい（フィールド 1・雑魚 1〜2 種・ボス 1）。**面積あたりの密度にすべてを注ぐ**。どの画面を切り取ってもヒーローショットであること。
- 「動く」「CI が通る」「予算内」は最低条件であって完成ではない。完成は §7 の品質ゲートを通ったとき。

## 1. 品質目標

| 観点 | 目標 | 参照 |
| --- | --- | --- |
| 画作り | 黄昏の墓地と礼拝堂。光・霧・密度で「灰に埋もれた古い世界」を一目で語る | Dark Souls III「灰の墓地」、Elden Ring リムグレイブ / ストームヴィル外縁 |
| 操作感 | 入力から反応まで 1〜2 フレーム、攻撃の重さ（ヒットストップ・振動・音・カメラ）がフロム作品と同等 | Elden Ring、Sekiro |
| 演出 | ボス入場・撃破・死亡・篝火・アイテム取得に専用の演出（カメラ・光・音・スロー） | 同上 |
| 性能 | モバイル（Xperia 1 V）60fps、PC 120fps 以上。プレイ中のスパイクなし | §5 |
| 起動 | 初回 5 秒以内に開始画面、2 回目以降 2 秒以内 | §4.4 |

## 2. 画作りの柱

1. **光が主役**: 低い太陽（黄昏）+ 高さ霧 + 体積光（ゴッドレイ）+ 篝火・ランタンの暖色。寒色の環境光と暖色の点光源の対比で構図を作る。空気遠近（遠景ほど霧の色に沈む）。カラーグレーディングは LUT で場所ごとに管理。
2. **密度**: 平らで空っぽの面を作らない。地形の起伏・小石・骨・瓦礫・枯れ草・苔・ひび・汚れのデカール。シルエットは複雑に（崩れた石積み、折れた柱、垂れ下がる布や鎖）。
3. **素材の説得力**: すべて PBR のテクスチャセット（ベースカラー / 法線 / ORM）。引き伸ばしは禁止（triplanar または正しい UV）。近景はディテール法線、地面は視差遮蔽（POM）。頂点ペイントで苔・泥・濡れをブレンド。
4. **動き**: 草木・布・旗・髪の風、炎の揺らぎと連動する光、灰と火の粉、カラス・虫、水面。静止画面を作らない。
5. **構図**: エリアごとに「ヒーローショット」（§7.1）を決め、そこから見える物・見えない物を設計する。遠景（城のスカイライン）は描き込んだインポスター / マットペイントで、近づけない場所にポリゴンを使わない。

## 3. 描画アーキテクチャ

### 3.1 エンジン

- **three.js r186（WebGPURenderer + TSL）を継続する**。ただし「three の既定機能を並べる」のではなく、**描画パイプラインを自前で設計する**。three は WebGPU バックエンドとノードシステム（コンピュート・ストレージバッファ・間接描画・render bundle を含む）として使う。
- 理由: 必要な最新手法（TAAU、GTAO、SSGI、SSR、ゴッドレイ、LUT、モーションブラー、DOF、クラスタードライト、ライトプローブグリッド、CSM）が r186 にノードとして揃っており、不足分は TSL / WGSL で書ける。エンジン移行（Babylon.js、Unity 等）は書き直しコストに対して上限が上がらない。上限を決めるのは手法とアセットであってエンジン名ではない。
- 足りない機能は自前で実装する。three の制約に合わせて品質を下げることはしない。

### 3.2 フレームの構成（目標形）

```
[GPU 駆動の準備]   コンピュート: 草・瓦礫・小物の視錐台 / 距離カリング → 間接描画の引数
[影]               太陽 CSM（2〜3 カスケード）。静的物はキャッシュし、動く物だけ毎フレーム描く
[深度プリパス]     不透明の深度 + 法線 + 速度（TAA・AO・SSR・モーションブラーが共有）
[不透明]           クラスタードライト（篝火・ランタン・エフェクトの光） + 焼き込み GI（ライトマップ / プローブ）
[画面空間]         GTAO（半解像度）、接触影、SSR（濡れた石・水だけ）
[体積]             フロクセルの体積霧（コンピュート）: 太陽・点光源の散乱、高さ霧
[半透明]           ソフトパーティクル、熱の揺らぎ（歪み）、デカール
[時間方向]         TAAU（内部 50〜75% 解像度から再構成。MSAA は廃止）
[ポスト]           物理ベースのブルーム（半解像度・エネルギー保存）、露出、AgX トーンマップ、LUT、
                   ビネット、フィルムグレイン、演出用 DOF・モーションブラー
```

### 3.3 ライティング

- **焼き込み GI**: Blender（ヘッドレス Cycles）でライトマップ（静的地形・建物）とライトプローブ（動く物用。`LightProbeGridNode`）を焼く。太陽の向き・時刻はエリアごとに固定する（焼き込みのため）。
- **実行時**: 太陽 CSM（静的キャッシュ）、クラスタードライト（点光源を数十個まで）、GTAO、接触影。
- 実行時のノイズ・手続き計算でライティングや模様を作らない（#240 の教訓）。

### 3.4 マテリアル

- 1 つの**ウーバーマテリアル**（TSL、機能フラグで分岐をコンパイル時に解決）に集約する。パイプライン数を抑え、見た目の一貫性を保つ。
- テクスチャはオフラインで生成・ベイクし、**KTX2（Basis）で GPU 圧縮**して配る。テクスチャ配列 / アトラスでドローコールを抑える。
- 特殊シェーディング: 肌（簡易 SSS）、布（シーン / ファズ）、金属鎧（異方性・摩耗のマスク）、濡れ。

### 3.5 ジオメトリ

- 環境は**高密度メッシュ**（Blender のスクリプトで手続きモデリング + ディスプレイスメント）。近景は数万三角形の岩・石積みも許容し、meshoptimizer で LOD 列を作る。
- 散布物（草・小石・骨・瓦礫）は**インスタンス + コンピュートカリング + 間接描画**で数万個規模。
- 遠景はインポスター。静的物は `BundleGroup` で記録を省く。
- 予算は**三角形数ではなく GPU 時間**で管理する（§5）。三角形を惜しんで面を平らにすることはしない。

### 3.6 キャラクター

- Quaternius UBC + UAL（等身、CC0）を基盤に、マテリアル（§3.4）、二次モーション（マント・装備の揺れ）、足の IK（地形への接地）、ルートモーション、アニメーションブレンドを作り込む。
- 敵・ボスは装備・汚れ・破損で個体差を付ける。

### 3.7 エフェクト

- 炎・煙・灰・血はオフラインのシミュレーション（Blender Mantaflow 等）から**フリップブック**を焼き、GPU パーティクル（コンピュート）で数千粒規模を描く。
- 打撃: 火花・血しぶき・デカール・カメラシェイク・ヒットストップ・振動を 1 つのイベントで束ねる。
- 敵の消滅・ボス撃破は専用シェーダとパーティクルで、ブルームに破綻のない値域で作る。

## 4. アセットパイプライン

### 4.1 構成

```
assets-src/        元データ（Blender スクリプト、生成パラメータ、ライセンス記録）
scripts/assets/    ビルド: Blender CLI（モデリング・UV・ベイク）→ gltf-transform（meshopt 圧縮・KTX2）
public/assets/     ビルド成果物（決定的に再生成できること）
```

- すべてのアセットはスクリプトから**決定的に再生成**できる。手作業の一点物を作らない。
- CI でアセットの検査（三角形数・テクスチャ解像度・UV の引き伸ばし率・法線の向き・ファイルサイズ）。`npm run assets:check`（`scripts/assets/check.mjs`）が形式・三角形数・テクスチャ解像度・ファイルサイズ・配信予算・内容ハッシュ名を検査する（UV の引き伸ばし率・法線の向きは未実装）。

### 4.2 調達

- ライセンスは CC0 のみ（[direction.md](direction.md) のオーナー決定を継続）。
- 作業環境から届かないサイト（Poly Haven、ambientCG など。高品質な CC0 の写真ベーステクスチャ・HDRI）は、必要なリストを作ってオーナーにダウンロードを依頼する。届かないことを理由に品質を下げない。
- 届く範囲では Blender の手続き生成で作る。

### 4.3 予算（配信）

- 初回ダウンロード: 合計 40MB 以内（圧縮後）。開始画面までに必要な分は 5MB 以内で、残りはロード中と遊んでいる間に段階的に読む。

### 4.4 起動

- シェーダはロード中にすべてコンパイルする（`GameView.warmUp`）。初出のエフェクト・敵・ボスでカクつかない。
- アセットは HTTP キャッシュが効く名前（内容ハッシュ）で配る。`public/assets/` は vite.config.ts がハッシュ名で書き出し、コードは `assetUrl()` で URL を作る。

## 5. 性能アーキテクチャ

### 5.1 目標

| 環境 | 品質 | 目標 |
| --- | --- | --- |
| Xperia 1 V | medium | 60fps（frame ≤ 16.7ms、GPU ≤ 12ms）、1% low ≥ 45fps |
| PC（オーナー環境） | high | 120fps 以上（GPU ≤ 6ms）。エフェクト中も |
| 共通 | — | プレイ中 33ms 超のスパイクなし。CPU（JS）≤ 4ms |

### 5.2 パス別 GPU 予算（モバイル medium の目安。実機の `?bench` で調整）

| パス | 予算 |
| --- | --- |
| 影（CSM、静的キャッシュ込み） | 1.5ms |
| 深度プリパス | 1.0ms |
| 不透明 | 4.0ms |
| GTAO + 接触影 | 1.0ms |
| 体積霧 | 1.0ms |
| 半透明・パーティクル | 1.0ms |
| TAAU | 0.8ms |
| ポスト（ブルーム・トーンマップ・LUT） | 1.2ms |
| 余裕 | 0.5ms |

- 品質段階（low / medium / high）は、上の各パスの解像度・サンプル数・距離を下げる形で作る。機能そのものを消すのは最後の手段。
  段階ごとの値は `src/render/quality/presets.ts` の `QualityPreset` に置き、各機能は `level` で分岐せずその値（機能フラグ・数値）を読む（#316）。
- 計測は `?bench`（#261）。性能に関わる PR は変更前後の実機値か、少なくともヘッドレスの CPU 時間を載せる。
- 三角形・ドローコールの予算（[performance.md](performance.md)）は CPU とメモリの上限として残すが、見た目を削る理由には使わない。

## 6. ゲームシステムによる補完

画面の外側にも品質はある。描画で足りない所は演出と設計で補う。

- **カメラ演出**: ボス入場のカット、撃破のスロー + 寄り、篝火で休むときのカメラ、致命の一撃の寄り。プレイ中のカメラは壁抜け・めり込みを起こさない。
- **視線の設計**: 近づけない場所はシルエットと霧で見せる。LOD の切り替わりが近距離（10m 以内）で見えない配置。
- **時間帯と天候**: エリアごとに固定（焼き込みと構図のため）。ボス戦は空と光を変えて場面転換を作る。
- **音**: 残響ゾーン、動的ミックス（ダッキング）、足音の材質、BGM の展開（#93 / #255）。
- **手応え**: ヒットストップ・振動・カメラシェイク・SE・エフェクトを 1 つの命中イベントで同期する。
- **UI**: 文字組み・余白・アニメーションまで作り込む。「YOU DIED」相当の画面、アイテム取得の表示。

## 7. 品質ゲート

### 7.1 ヒーローショット

エリアごとに固定のカメラ視点を 3〜5 個決める（篝火・墓地・礼拝堂の門・地下墓所・中庭・霧の門・闘技場・地下水路）。

- 見た目に関わる PR は**変更前後の全ヒーローショット**（`npm run heroshots`、下記）を PR に載せる。
- オーケストレーター（技術責任者）が参照作品の水準と比べて判定する。見劣りすれば差し戻す。

撮影は 1 コマンド（`scripts/heroShots.mjs`）。

```sh
# 変更前（main を checkout した worktree など）で
npm run heroshots -- /tmp/hero-before
# 変更後で
npm run heroshots -- shots/hero-after --compare /tmp/hero-before
```

- 出力: `<ディレクトリ>/<視点名>.png`、全ショットを並べた `contact-sheet.png`、撮影条件の `index.json`。`--compare <変更前>` を付けると、変更前と左右に並べた `compare-sheet.png` を変更後のディレクトリに出す。PR には `compare-sheet.png`（と気になる視点の単体）を貼る。
- 引数: 品質 `high`（PC の既定）/ `medium`（`--mobile` の既定。基準機相当）。`--mobile` で 915x412 DPR3（既定は PC 1280x720）。`--only bonfire-arrival,闘技場` で名前またはエリアを絞る。`--no-shoot` で撮影せずに sheet だけ作り直す。解像度は `?scale=1` で固定（動的解像度で荒れない）、HUD は隠す。
- 環境変数: `HERO_PORT`（既定 4176）、`HERO_SKIP_BUILD=1`（ビルド済みの `dist/` を使う）、`HERO_VIEWS`（視点データの差し替え）。
- 視点は `scripts/heroShots.json`（エリアごとに 2〜3、計 20。篝火・墓地・礼拝堂の門・礼拝堂内部・地下水路・地下墓所・中庭・霧の門・闘技場（ボスあり）・ショートカット）。追加・変更はこのファイルだけでよい（形式はファイル先頭の `$doc`）。プレイヤーの位置と向き（`face` で注視点を向ける）、三人称カメラのずれ・距離・ピッチ、自由視点（`freeCam`）、敵の有無（`enemies: false`）、`window.__game.dev` のフック呼び出し（`dev`: ボスを出す・床板を割るなど）を書ける。構図はゲーム中の三人称カメラ（距離 4.2m・ピッチ 12°）を基本にする。
- 待ち・再現性: 同じビルド・同じ視点なら同じ画像になる（実 GPU で 21 視点を 2 回ずつ撮り、画素差 0 を確認済み）。ページは `?shot` で開き、描画側の時計（`src/render/renderClock.ts`。パーティクル・炎や松明の揺らぎ・TSL の `time`・局所光源・アニメーションのミキサーの dt と時刻の源）をロード直後から止めておく。開始は一時停止のまま（`dev.start({ paused: true })`）で、実時間ではシミュレーションを進めない。視点ごとにシミュレーションを止めて状態を作り、`dev.advance(steps)`（既定 60 ステップ）で接地・アニメーション・カメラ追従を落ち着かせてから、`dev.renderFrames(n)`（既定 12 枚。1 枚ごとに 1/60 秒ずつ描画時計を進めて同期的に描く）でパーティクル・ムードの立ち上がりを作る。rAF の描画では時計が進まない（同じ絵を描き直すだけ）。実時間では待たない。アセット読み込みと初回シェーダコンパイルは開始画面（`data-state=ready`）の前に済んでいる。同じ `--only` の組み合わせなら再現するが、1 ページで複数視点を順に撮るため、視点の選び方（撮影順）を変えると積算時計（炎の位相など）は変わる。比較は同じ視点の組み合わせで撮る。
- SwiftShader（CI 相当のヘッドレス）では 1 枚あたり 1〜2 分、PC 20 枚で 30〜40 分かかる。構図を調整するときは `--only` と `HERO_SKIP_BUILD=1` で回す。

### 7.2 見た目の不合格条件（1 つでもあれば差し戻し）

- テクスチャの引き伸ばし、継ぎ目、模様の筋（バンディング・等高線）
- 浮いている・めり込んでいる物（草・小物・キャラクター）
- 平らで何もない面が画面の 1/4 以上
- 10m 以内で見える LOD の切り替わり、ポップイン
- エイリアシングのちらつき、白飛び・黒つぶれ（意図しないもの）
- 意図しない粒子・破片（何か分からない物が画面を横切る）

### 7.3 バグの優先度

見た目のバグ（上の不合格条件に当たるもの）は機能追加より優先する。

## 8. ロードマップ

| 段階 | 内容 | 終わりの条件 |
| --- | --- | --- |
| 0. 止血 | 見た目のバグ（飛び交う破片・崖の引き伸ばし・等高線）、`?bench`、CPU 削減、消滅エフェクト | 不合格条件のバグがない。実機の基準値が取れている |
| 1. 描画の基盤 | フレーム構成（§3.2）: TAAU、深度・速度プリパス、CSM 静的キャッシュ、GTAO、体積霧、ブルームの作り直し、LUT。ウーバーマテリアル、KTX2 パイプライン、焼き込み GI のパイプライン | テストシーンで全パスが予算内で動く |
| 2. ゴールデンエリア | 篝火〜墓地を最終品質まで作り込む（地形・崖・石積み・散布物・デカール・光・霧・音）。他エリアの手本にする | ヒーローショットがゲートを通る |
| 3. 全エリア展開 | 礼拝堂・地下墓所・中庭・闘技場・地下水路を同水準に | 全ヒーローショットがゲートを通る |
| 4. キャラクターと演出 | マテリアル・二次モーション・IK、エフェクトのフリップブック化、カメラ演出、UI | 戦闘・ボス戦の動画がゲートを通る |
| 5. 仕上げ | 性能・起動時間・全体の磨き込み | §1・§5 の目標をすべて満たす |

- 段階 0〜2 の間、新しいゲームプレイ機能の追加は止める（着手済みのものとバグ修正を除く）。
