# 作業エージェント共通手順（オーケストレーター作成）

リポジトリ: Kiikurage/game-test（ブラウザ向けエルデンリングライク 3D TPS。Three.js WebGPU 専用、スマホ対応、基準機 Xperia 1 V、ボリュームより作り込みの完成度を最優先）。

## 開始時
1. `AGENTS.md`（開発コマンド・依存方向）、`docs/direction.md`、`docs/vertical-slice.md`（ゲーム仕様。担当チケットに記載の節は必読）、必要に応じ `docs/assets.md` を読む。
2. GitHub MCP ツールを ToolSearch で読み込む:
   `select:mcp__github__issue_read,mcp__github__issue_write,mcp__github__add_issue_comment,mcp__github__create_pull_request,mcp__github__pull_request_read,mcp__github__actions_list,mcp__github__get_job_logs`
   owner=Kiikurage, repo=game-test。gh CLI は使えない。
3. 担当 Issue を読み、AGENTS.md 2.3 の手順で確保: 状態ラベル（`status:ready` または `status:blocked`）を外して `status:in-progress` と `agent:<自分の名前>` を付ける（type/area ラベルは残す）。assignee=Kiikurage。着手コメント。依存先が未クローズでもオーケストレーターが割り振った場合は着手してよい（依存先は main にマージ済みのはず）。
4. `git fetch origin main && git checkout -b <type>/<番号>-<短い英語名> origin/main` → `npm ci`。

## 実装
- 完了条件をすべて満たす。仕様書の数値に従う（変える場合は理由を PR に書く）。
- three r186 の API は `node_modules/three` のソース・examples で確認する（記憶に頼らない）。
- 見た目に関わる変更は `npm run shot`（`SHOT_QUERY` 等の環境変数は scripts/shot.mjs 参照）で撮影し、自分で画像を Read して確認・改善する。
- ロジックはユニットテスト（Vitest）、統合は E2E（Playwright、ヘッドレス WebGPU）で検証。SwiftShader は遅いので、ロジック検証の E2E は `?quality=low&scale=0.25` で開く。E2E のポート競合を避けるため `E2E_PORT` を 4100〜4999 のランダムな値にして実行する。
- 共有ファイル（main.ts、gameView.ts など）の変更は必要最小限に。並行して他エージェントが作業している。
- CPU 節約: コンテナは 4 コアを複数エージェントで共有している。ビルド・E2E・撮影（SwiftShader は CPU を大量に使う）は必要な時だけ、1 つずつ実行し、並列に走らせない。撮影は確認したい視点だけ。
- ディスク節約: Playwright の --output やログをリポジトリ外・ルート直下に書かない。test-results/ と shots/ は終わったら削除する。
- タイムボックス: 着手から 90 分で PR を出す。見た目の試行（撮影）は合計 8 回まで。固定時間の sleep で待たない。

## 完了時
1. `npm run lint && npm run typecheck && npm test && npm run build` が通る。E2E は**変更に関係する spec だけ**をローカルで実行（例: `npx playwright test e2e/enemy.spec.ts --workers=1`）。**E2E 全件はローカルで流さない**。全件は CI に任せる。
2. コミット（英語命令形）。末尾トレーラーはシステムの attribution 指示に従う。
3. push 直前に `git fetch origin main && git merge origin/main`（rebase・force-push 禁止）で追従し、競合を解消して再チェック。
4. 各ブランチは origin/main から切る。`git push -u origin <branch>` → PR 作成（base=main、本文: 変更内容 / 確認方法 / 未対応事項、`Closes #<番号>`、末尾に `🤖 Generated with [Claude Code](https://claude.com/claude-code)`）→ Issue を `status:in-review` に。
5. **CI の完了を待たない**。push / PR 作成後は、CI の結果を待ってポーリングや Monitor でブロックせず、すぐに最終報告（「PR #N 作成、CI 待機中」）を返してターンを終える。CI の結果はオーケストレーターが PR を購読して受け取り、赤なら失敗内容を添えてあなたを再開する（SendMessage）。再開されたら原因を直して push し、再び待機中として報告して終える。PR が main と競合していると CI は起動しないので、報告前に main をマージしておく。
6. GitHub に投稿するコメント本文の末尾には `\n\n---\n_Generated by [Claude Code](https://claude.ai/code)_` を付ける。
7. マージはしない（オーケストレーターが行う）。

## 報告（最終メッセージ、300字以内）
